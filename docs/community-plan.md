# Helping UniWay reach people

We want the project to be useful enough that people choose to share it. Public visibility alone does not create a community.

## Make the first five minutes easy

Keep the README focused on the student problem, a working local setup and honest boundaries. Add a short real screen recording after browser verification. Show upload, review and directions rather than promising automatic accuracy. Use relevant GitHub topics such as `campus-navigation`, `wayfinding`, `react`, `typescript`, `ocr` and `accessibility` when repository metadata access is available. Topics and readable documentation help discovery; they do not guarantee reach.

## Invite useful contributions

Start with small tasks: test one phone journey, improve one empty state, add one permitted OCR fixture or review a translation. Use issue labels for confirmed bugs, help wanted and good first issues once issues exist. Keep one branch and pull request per step, and explain validation so newcomers can follow the reasoning.

## Share after proof

First collect feedback from a small university group with permission. Publish a concise demo and release notes in relevant student and open-source communities only when the device checks support the claims. Ask for a specific kind of feedback. Do not mass-message people or post in communities without following their rules. No outreach messages have been sent by this work.

Track concrete results: successful first runs, reproducible bug reports, device coverage and merged contributions. Stars are encouraging, but they do not tell us whether a fresher reached the right room.

## Maintainer setup still needed

Configure private vulnerability reporting and a community contact; enable Discussions if desired; add repository topics; consider branch protection after CI runs successfully. These administration settings are not implied by adding files.
